# Zeroshot on ProgramBench

A reproducible, fully containerized benchmark of a minimal Zeroshot graph on
[ProgramBench](https://github.com/facebookresearch/ProgramBench): rebuild a program from its
compiled reference executable and documentation, offline, then score the rebuild with
ProgramBench's hidden behavioral tests.

## Question

**H1 — "Don't trust, verify":** with the same model and the same generic builder prompt, does an
independent check-and-repair loop improve the hidden-test pass rate?

The first experiment (`experiments/luna-xhigh-svgbob.json`) runs GPT-5.6 Luna at `xhigh` effort on
`ivanceras__svgbob.6d00ad9` (ASCII diagrams to SVG; 472 scored tests; best public score 65%):

| Arm | Graph | Runs |
|---|---|---|
| `loop` | `build → check`, repeated until the check accepts (at most 4 rounds) | 5 |
| `single` | `build` once | 3 |

Runs are interleaved in a fixed, pre-registered order (`L S L L S L S L`). Every loop run is
snapshotted when each build finishes, so the workspace after the first build is a same-run,
single-worker baseline. The pre-registered decision rule (paired gain = final score minus
first-build score, loop arm):

- **supported**: every loop run gains, and the mean gain is at least 5 points;
- **refuted**: the mean gain is under 2 points;
- otherwise **inconclusive**.

## The graph and prompts

Both arms share one byte-identical `build` node. Round 1 of the loop is exactly the single arm.

```
loop "solve" (max 4 rounds; stop when check.verdict = accepted)
  build  — Codex, keeps its own session across rounds; input = task + feedback ("" in round 1)
  check  — Codex, fresh session every round; verdict accepted | rejected; its diagnostic
           becomes the builder's feedback for the next round
```

The only text we wrote is two generic role prompts, frozen before any run
(`prompts/builder.md`, `prompts/checker.md`):

> **Builder:** Complete the task described in the input. Keep working and verifying your own work
> until you believe the result fully satisfies the task. If review feedback is provided, address
> every point without breaking what already works.

> **Checker:** Independently judge whether the current workspace satisfies the task. Derive your own
> checks from the task statement and whatever it makes available; do not rely on the builder's
> tests, notes, or claims. Run the checks. Accept only with concrete evidence that nothing is wrong.
> Otherwise reject and list the most important discrepancies, each with a minimal reproduction.

All task knowledge comes from the benchmark's own task statement (`prompts/task.md`). It is
generated by `scripts/build_task_prompt.py` from the upstream mini-SWE-agent ProgramBench prompt
(`prompts/upstream/`, commit `04d809ce`). The script removes only the scaffold mechanics (the
persona line, the one-bash-command protocol, the submit sentinel, and command examples); every
other line is verbatim. Zeroshot adds its standard node guidance around each prompt.

## Environment and isolation

- **Task environment:** the official ProgramBench task image, pinned by digest, unchanged except
  for Zeroshot, Codex's full platform package (the CLI plus its `codex-code-mode-host` tool
  runner and `rg`, checksum-pinned releases), and a Codex config. The agent runs
  as the image's non-root `agent` user with `SYS_PTRACE` dropped, like the upstream baseline. The
  reference executable is execute-only. The image's own sudo rules (package managers, cargo, go)
  are left as ProgramBench ships them.
- **Network:** agent containers sit on an internal Docker network whose only exit is a tinyproxy
  that allows HTTPS `CONNECT` to `api.openai.com` and nothing else. Codex web search is disabled
  (it runs server-side and would bypass the proxy). Codex's own background requests (plugin and
  account endpoints on github.com and chatgpt.com) are refused and show up in `proxy.log`. The
  upstream baseline used `--network none`, which is impossible here because the agent itself
  calls the model API.
- **Secrets:** the API key reaches Zeroshot only through `docker exec -e OPENAI_API_KEY` (never
  argv, never an image layer). Tool commands must not see it: the Codex config applies its
  KEY/SECRET/TOKEN exclusions explicitly and turns off Codex's shell snapshot, which otherwise
  re-exports the whole process environment (including the key) into tool shells. The smoke test
  proves this from inside a real run (`KEY_VARS_VISIBLE=0`). A same-user process could still read
  `/proc/*/environ`; the audit flags that, and every artifact, including archive contents, is
  scanned for the literal key.
- **Tooling parity:** Zeroshot starts Codex with a minimal environment, so the rendered Codex
  config mirrors the task image's ENV (`CARGO_HOME`, `RUSTUP_HOME`, …) into tool commands.

## Reproduce

Requirements: Linux x86_64, Docker 24+, about 40 GB free disk, an OpenAI API key with access to
the model.

```bash
git clone --branch benchmark/programbench https://github.com/the-open-engine/zeroshot.git
cd zeroshot/benchmarks/programbench
export OPENAI_API_KEY=...            # or: scripts/push-openai-key.sh user@host for a remote box
scripts/zsbench smoke                # ~20 min, a few dollars: isolation, diagnostics, pipeline, scoring fidelity
scripts/zsbench run experiments/luna-xhigh-svgbob.json
```

`scripts/zsbench` builds the runner image (`Dockerfile`) and runs it with the host Docker socket
mounted. The runner builds the proxy and agent images, runs the attempts, evaluates them with
`programbench eval`, and writes `results/<experiment>/summary.md`. Long runs:
`ZSBENCH_DETACH=1 scripts/zsbench run …`, then `docker logs -f zsbench-runner`.

Other commands: `plan` (render graphs and the attempt order), `check-key`, `eval` (re-score),
`report`, `cleanup`. Unit tests: `python -m unittest discover -s tests`.

## Results layout

```
results/<experiment>/
  manifest.json          pins, image digests, rendered Codex config, prompts, host
  summary.md|json        per-run table, per-arm aggregates, H1 decision, audits
  scores.json            leaderboard-comparable score for every final and snapshot
  scores-per-test.json   pass/fail per hidden test
  proxy.log              every egress request (allowed and refused)
  attempts/NN-arm/
    attempt.json         timing, terminal status, verdicts, errors
    run/                 the exact graph, runtime plan, and input submitted
    watch.ndjson         Zeroshot status projections (active executions, cursor)
    snapshots/           workspace after each build (build-N) and each check (check-N)
    submission.tar.gz    final workspace (the reference binary excluded)
    trajectories.tar.gz  Codex sessions and the Zeroshot ledger
  evals/                 programbench eval outputs per archive
```

## Scoring and cost

- **Score:** `programbench eval` (v1.2.4, the leaderboard's version) on the `task_cleanroom_v6`
  image, then ProgramBench's own `test_results_map`/`score_from_tests` with the leaderboard
  registry's ignore list pinned at commit `794fa30`. `programbench info` prints unfiltered counts
  and is not comparable. The smoke test re-scores a published leaderboard submission on the same
  task and requires agreement within 2 points (observed: 53.8% vs 53.6%).
- **Cost:** per-node token usage from Zeroshot's ledger, priced from the experiment's pricing table
  (input, cache reads, cache writes, output).
- **Audits:** Codex transcripts are scanned for commands that inspect or copy the reference binary,
  fetch from the network, use sudo, read cached dependency sources, or read harness internals, and
  for web-search calls. Checker rounds are diffed to confirm verifiers did not edit the workspace.
  Findings are reported for human review, not auto-disqualified.

## Known deviations from the public leaderboard setup

- **Harness:** Zeroshot driving the Codex CLI, not mini-SWE-agent. Compare arms within this
  benchmark; leaderboard numbers are context.
- **Network:** the model API is reachable (see above).
- **Limits:** 6 hours wall clock per attempt (as upstream); 3 hours per build node, 1 hour per
  check. No step limit.
- **Harness internals:** the builder could in principle read the graph (including the checker
  prompt) from Zeroshot's state directory. The audit flags any such access.
- **Scope:** one task. Generality needs a follow-up panel of tasks drawn at random.
